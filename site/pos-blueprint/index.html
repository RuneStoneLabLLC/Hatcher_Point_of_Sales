Service blueprint

Small-Store POS System

A practical plan for building a modern point-of-sale platform that handles retail checkout, inventory, cost control, cash management, reporting, payments, and gift cards while keeping payment risk outside the custom application.

Sections Core Position Architecture Retail Checkout Inventory Cost Control Cash Management Analytics Payments Gift Cards Security Offline Mode Build Phases

Core Position

Build the POS around retail operations, not card processing. The system should own products, checkout, inventory, users, reports, cash drawers, gift cards, and receipts. Card payments should be handled through a certified payment provider and certified terminals.

Guiding rule: own the retail workflow, outsource the payment risk.

Build in-house

Register app, admin dashboard, catalog, inventory, reporting, gift cards, permissions, and audit logs.

Integrate

Card terminals, gateway authorization, capture, voids, refunds, settlement, and payment tokens.

Recommended Architecture

Use a modern web-based architecture first. It is easier to deploy, update, support, and host on Railway while still working well on registers, tablets, and phones.

  • Frontend: React, Vue, Svelte, or another modern web framework.
  • Backend: Node.js/NestJS, Laravel, Django, or .NET.
  • Database: PostgreSQL.
  • Hosting: Railway for the cloud backend and database.
  • Offline storage: IndexedDB in the browser.
  • Authentication: role-based users with MFA for admins.
  • Payments: Stripe Terminal, Square Terminal API, Clover, TSYS/Global Payments, or another terminal-supported provider.
  • Receipts: browser print first, then network receipt printers or ESC/POS integration.
  • Barcode scanning: USB scanner input first, camera scanning later.

Retail / POS / Checkout

The checkout screen should be fast, simple, and hard to break. Employees should be able to scan, search, discount, tender, and print receipts with minimal steps.

Required Features

  • Product search and category browsing.
  • Barcode scan entry.
  • Cart quantity changes.
  • Price override with manager permission.
  • Discounts, returns, exchanges, and suspended tickets.
  • Customer lookup.
  • Cash, card, gift card, and split tender.
  • Printed, emailed, or texted receipts.

Core Data Entities

Sale, SaleLineItem, Payment, Refund, Discount, TaxLine, Customer, RegisterSession, and CashDrawerEvent.

Completed sales should be immutable. Corrections should happen through refunds, voids, or adjustment transactions.

Inventory

Inventory should be event-based. Instead of only changing a quantity field, the system should record every movement that caused the quantity to change.

Movement Types

  • Sale
  • Return
  • Receive stock
  • Manual adjustment
  • Damage
  • Shrink
  • Transfer
  • Vendor return

Minimum Product Fields

SKU, barcode, product name, category, vendor, cost, retail price, tax status, current quantity, reorder point, active status, and stock adjustment history.

Cost Control

Cost control turns the POS from a register into a business system. Item cost needs to be captured early so margin, shrink, and inventory value are useful later.

  • Default cost.
  • Last received cost.
  • Average cost.
  • Retail price.
  • Gross margin.
  • Vendor.
  • Reorder quantity.
  • Shrink and damage tracking.

Cash Management

Cash should be tied to register sessions so every drawer has a clear opening count, closing count, expected cash amount, actual cash amount, and variance.

Opening

Manager opens the register and enters the starting cash amount.

During the day

Cash sales, refunds, paid-in, paid-out, and cash drops are tracked.

Closing

Employee enters actual cash and the system compares it against expected cash.

Review

Variance is logged and routed for manager review.

Analytics And Reporting

Start with reports that help the owner run the store. Add forecasting and advanced dashboards only after the core data is reliable.

  • Daily sales.
  • Sales by payment type.
  • Sales by product and category.
  • Tax collected.
  • Refunds, discounts, and voids.
  • Cash drawer variance.
  • Inventory value.
  • Low stock.
  • Gross margin.
  • Top products.
  • Staff sales activity.
  • CSV exports.

Payments And Gateway Options

Create a payment provider abstraction so the POS can support one provider at launch and add others later without rewriting checkout.

Provider Interface

createPaymentIntent(), sendToTerminal(), capturePayment(), voidPayment(), refundPayment(), and getTransactionStatus().

Store Only Safe Payment Metadata

  • Payment provider.
  • Provider transaction ID.
  • Authorization code.
  • Payment status.
  • Card brand.
  • Last four digits.
  • Entry method.
  • Amount and timestamp.

Never store full card numbers, CVV, PIN, magnetic stripe data, or raw EMV data.

Gift Cards

Gift cards can be an internal store-credit system, but they need strong audit controls because they behave like money inside the store.

  • Sell gift card.
  • Redeem gift card.
  • Check balance.
  • Reload card.
  • Void unused card.
  • Transfer balance.
  • Manual adjustment with manager permission.
  • Full gift card transaction history.

Use random card numbers or codes. Avoid simple sequential numbers. Store lookup tokens securely and keep full audit logs.

Security Blueprint

The system should assume every important action needs server-side validation, role checks, and an audit trail.

  • HTTPS everywhere.
  • Strong password hashing.
  • MFA for owner and admin users.
  • Role-based permissions.
  • Audit logs for sensitive actions.
  • Device and session management.
  • Encrypted secrets.
  • Database backups.
  • Least-privilege database users.
  • No card data storage.
  • Regular dependency updates.
  • Manager approval for refunds, voids, discounts, and cash adjustments.

Offline Mode

Offline mode matters for a real store, but it should be designed conservatively.

  • Cache the product catalog locally.
  • Allow cash transactions while offline.
  • Queue non-card sales locally.
  • Sync when online.
  • Prevent gift card redemption offline unless the balance can be verified.
  • Use card payment provider offline mode only if officially supported.
  • Clearly mark unsynced transactions.

Build Phases

Build the operational POS first, then add payment complexity after checkout and inventory are stable.

Phase 1
MVP Register

Login, product catalog, barcode scanning, cart, tax, cash checkout, receipt, sales history, and register open/close.

Phase 2
Inventory

Product management, categories, vendors, stock counts, inventory movements, low-stock alerts, purchase receiving, and CSV import/export.

Phase 3
Card Payments

One payment provider, certified terminal flow, refunds, voids, payment reports, and safe payment metadata only.

Phase 4
Reporting

Daily sales, cash drawer, inventory value, margin, sales by category/product, and exports.

Phase 5
Gift Cards

Issue, redeem, reload, balance lookup, and adjustment audit trail.

Phase 6
Advanced Features

Multiple locations, stock transfers, ecommerce bridge, loyalty, accounting export, and advanced analytics.
